# Scoop bucket template

A reusable starting point for publishing Windows applications and Python
command-line tools through [Scoop](https://scoop.sh). It includes manifest
scaffolding, scheduled and release-triggered updates, Windows install tests, and
a generated package catalog.

## Start a bucket

1. Create a repository from this template.
2. Replace the placeholder copyright line in `LICENSE`.
3. Replace this README title and introduction with your bucket's name and
   purpose.
4. In **Settings → Actions → General**, give workflows read and write access and
   allow GitHub Actions to create pull requests.
5. Run `mise install`, then add the first manifest with
   `mise run add-manifest shim <package>` or
   `mise run add-manifest binary <owner>/<repository>`.
6. Run `mise run generate-readme` and commit the generated table with the new
   manifest.
7. Run `mise run check` before opening a pull request.

No owner or repository substitutions are needed in scripts or workflows. Shim
manifests infer the GitHub repository from the `origin` remote so they can point
to the checked-in `scripts/noop.ps1`. For a downloaded archive or another remote,
set `SCOOP_BUCKET_REPOSITORY=owner/repository` or pass `--bucket-repository`.

## Install packages

```powershell
scoop bucket add <bucket-name> https://github.com/<owner>/<repository>
scoop install <bucket-name>/<package>
```

## Packages

The template supports three install routes:

- **Binary** downloads a prebuilt Windows `.zip` and shims its `.exe`.
- **pipx shim** installs a Python CLI from PyPI through `pipx`.
- **uv-tool shim** installs a Python CLI from PyPI through `uv`, which manages
  its own Python runtime.

## Add a manifest

The standard-library-only scaffolder fetches upstream metadata and writes the
appropriate JSON manifest:

```sh
# PyPI package installed with uv (default) or pipx
mise run add-manifest shim <package>
mise run add-manifest shim <package> --via pipx

# Prebuilt .zip from a GitHub release
GITHUB_TOKEN="$(gh auth token)" mise run add-manifest binary <owner>/<repository>
mise run add-manifest binary <owner>/<repository> --artifact <file.zip>

# Seed a binary before its first release
mise run add-manifest binary <owner>/<repository> --seed --bin <command.exe>
```

When the bucket is not a GitHub clone, add
`--bucket-repository <owner>/<repository>` to a shim command. Use
`--bucket-ref <branch>` if `noop.ps1` is served from a ref other than `main`.

Review inferred descriptions, licenses, archive layout, and commands before
committing. The Windows workflow defaults to `<command> version`; add an entry to
the `$smoke` map in `.github/workflows/tests.yml` when a package uses a different
smoke test.

## Validate changes

```sh
mise install
mise run check
```

CI additionally validates every manifest and installs each non-placeholder
package on Windows.

## Automated updates

The weekly workflow checks every manifest and opens a pull request when upstream
versions change. A package repository can request an immediate update after a
release with a `repository_dispatch` event of type `update-manifest`:

```json
{"package":"example","version":"1.2.3"}
```

`package` is required and selects a manifest family, so `example` also selects
`example-pipx`. `version` is optional and informational because the updater
re-checks the configured upstream source. A producer needs a fine-grained token
with **Contents: write** access to this bucket solely to call the dispatch API.
Store that token in the producer repository, not in the bucket.

Automated pull requests use the repository secret `WORKFLOW_TOKEN` if defined,
falling back to `GITHUB_TOKEN`. Because GitHub suppresses follow-on workflow
runs for actions performed by `GITHUB_TOKEN`, configure a PAT or GitHub App token
as `WORKFLOW_TOKEN` to run CI checks automatically on update PRs, or run the
`Tests` workflow manually via `workflow_dispatch`.

## Managed boilerplate

`.gitignore` is generated from GitHub's macOS, Windows, Linux, Visual Studio Code,
and Python templates with [Cobo](https://github.com/hasansezertasan/cobo). Its
exact inputs are recorded in `cobo.lock`.

```sh
cobo check --strict
cobo sync
```

Do not edit Cobo-managed blocks by hand; update their inputs and re-render them.
